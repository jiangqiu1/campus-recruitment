# 认证模块 · 原理文档

> 说明设计意图、业务流程与数据流。代码定位见「实现文档」。

## 1. 设计目标

- **无状态认证**：服务端不存 session，靠 JWT 自包含用户信息，天然支持水平扩展。
- **可控失效**：JWT 本身"签发后不可撤销"，因此引入 Redis 黑名单 + token 版本号，实现"退出即失效"和"改密码即失效"。
- **单端登录**：同一账号新登录会顶掉旧 token。

## 2. 登录流程

```
客户端                    后端                          Redis
  │  POST /auth/login       │                             │
  │ ──────────────────────► │ 1. userService.login 校验    │
  │                         │    (用户存在→BCrypt→角色→状态) │
  │                         │ 2. 生成 tokenVersion(UUID前12)│
  │                         │ ───────────────────────────► │ set token:version:{id}
  │                         │ 3. jwtUtil.generateToken(...) │
  │                         │ ───────────────────────────► │ set token:{id}
  │ ◄───── Bearer token ─── │ 4. 返回 prefix+token + 用户信息│
```

关键点：
1. `UserServiceImpl.login`（35 行）依次校验：用户存在 → BCrypt 密码匹配 → 角色匹配（可选）→ 账号状态。
2. token 内含 `tokenVersion`（UUID 去横线前 12 位）。
3. Redis 存两份：`token:{userId}`（单端登录依据）、`token:version:{userId}`（改密码失效依据）。

## 3. 拦截器 7 步校验

`JwtInterceptor.preHandle`（37 行）：

| 步骤 | 校验内容 | 失败返回 |
|------|---------|---------|
| 1 | 取 Authorization 头，必须以 `Bearer ` 开头 | 401 未授权 |
| 2 | 去前缀得纯 token | — |
| 3 | 解析 claims | 401 Token 无效 |
| 4 | 是否过期 | 401 Token 已过期 |
| 5 | 读 `token:{userId}`，若存在且 ≠ 当前 token | 401 账号已在其他地方登录 |
| 6 | 读 `token:version:{userId}`，与 claim 中 tokenVersion 比较 | 401 密码已修改 |
| 7 | 通过后写 `request.setAttribute`（userId/username/role） | — |

## 4. 登出与改密码的失效机制

**登出**（`AuthController.logout`，99 行）：token 写入 `blacklist:{token}`，TTL 7 天。

**改密码**（`AuthController.updatePassword`，193 行）：更新密码后，重新生成新的 `tokenVersion` 覆盖 `token:version:{userId}`。由于旧 token 的 claim 里还是旧版本号，会在拦截器第 6 步被拒。

## 5. 已知问题

- **黑名单未闭环**：`JwtInterceptor` 本身不查 `blacklist:`，只有 `/auth/me`（`getCurrentUser` 220 行）手动校验。即登出后的 token 仍可通过拦截器访问其它接口。这是后续需修复的安全隐患。

## 6. 密码安全

`PasswordEncoderConfig` 定义 `BCryptPasswordEncoder(8)`（strength=8）。登录用 `matches` 比对，注册/改密码/重置用 `encode` 加密，数据库只存密文。

## 7. 角色体系

`UserRoleEnum`：0=学生 STUDENT、1=教师 TEACHER、2=企业HR HR、3=管理员 ADMIN。角色写在 JWT claim 中，`BaseController.getCurrentRole()`（43 行）从 request attribute 读取，配合 `requireTeacher/requireHr/requireAdmin` 做接口级鉴权。
